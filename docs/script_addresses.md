# Battle bytecode address milestone

Status: investigation and local probes complete; runtime milestone open. The complete lexical operand inventory is script_address_inventory.json, generated by `python3 tools/audit_validation.py`. It lists 202 four-byte operand sites across battle_script.inc and battle_ai_script.inc, plus 249 candidate pointer/numeric reads in src/battle*.c. Each entry includes macro/source/line/expression. This is not an assertion that all 202 operands are pointers: semantic closure and non-macro raw data relocations still require review.

## Source assumptions

`asm/macros/battle_script.inc` emits four-byte absolute label/data addresses. Examples: accuracycheck carries a failure script pointer; goto/call carry script pointers; jumpifbyte/halfword/word carry a data pointer and a branch pointer; setbyte/addbyte/copyarray carry writable data pointers. jumpifword also carries a numeric word value; status masks and orword masks are numeric. A name such as `value` does not classify an operand: decrementmultihit uses it as a branch destination. AI macros have their own pointer operands and fixed widths.

`include/global.h:T1_READ_PTR` casts T1_READ_32 to u8*, and T2_READ_PTR similarly casts T2_READ_32 to void*. These encode a little-endian 32-bit address assumption. Some handlers use READ_32 with explicit casts, so changing only READ_PTR would be insufficient. Normal u32 flags, damage values, RNG states and status masks must remain numeric.

`gBattlescriptCurrInstr` is a native const u8* cursor. Cmd_goto loads an encoded target. Cmd_call pushes cursor+5, then reads its four-byte target; Cmd_return pops it. `BattleScriptsStack` stores eight native pointers and a size; BattleScriptPush/PushCursor/Pop maintain them. BattleCallbacksStack holds actual C function pointers and is a separate semantic type. AI also uses a script cursor and the stack type. C tables and gBattleScriptsForMoveEffects can refer directly to scripts; bytecode additionally refers to strings/data/writable battle globals and code elsewhere. A single script-base offset does not represent every such reference.

Widening `.4byte` operands to eight bytes breaks hard-coded instruction lengths, offsets and saved cursor+5 returns. A global u32-to-pointer replacement corrupts numeric operands. GBA-style memory-mapped register macros are another address class outside bytecode; they need device emulation or explicit platform adapters, not the script decoder.

## Approaches evaluated

### A — 32-bit process

Local tests compiled a native pointer probe and attempted both `cc -m32` and `cc -arch i386`; diagnostics are saved in address_toolchain_probe.json. Native pointers were eight bytes and the observed static address exceeded UINT32_MAX. -m32 failed to link for the selected target; i386 failed because the macOS SDK lacks that library architecture. No working 32-bit executable was produced.

On a supported 32-bit Linux toolchain, four-byte native pointers could preserve widths if scripts are reassembled/linked to that executable's addresses, relocations fit and byte order/alignment are verified. Original ROM addresses still would not automatically identify host objects. GBA I/O and controller dependencies remain. Potential performance is high, but portability and legacy library support are poor; debugging mixed host/GBA assumptions remains difficult. No fidelity claim or performance measurement follows from process width alone.

### B — address relocation/virtual address map

Preserving four-byte fields with typed virtual addresses is the preferred future native optimization. A checked resolver could map script ROM, constant data and writable global regions into host objects while preserving offsets. It must distinguish script/data/function references and null, validate bounds, and handle explicit READ_32 casts and C-to-script references. The central READ_PTR abstraction is a start, not the full adaptation. Relocation must be generated from symbol/operand metadata; numeric immediates stay untouched.

This can be portable and deterministic with stable IDs. It changes operand interpretation rather than move logic, but missing one writable/data reference can silently change behavior. Debugging is manageable with virtual address traces; maintenance cost is higher than an emulator. Throughput is unmeasured. No relocation backend has been implemented or validated.

### C — native-width operands

Reassembling pointer operands using uintptr_t is technically possible only with typed macro metadata and regenerated interpreter offsets/widths, including AI and return addresses. It would require widespread changes or a generated interpreter/layout specification. It offers native performance but the largest instruction-layout regression surface and maintenance burden among the native approaches. Determinism alone would not establish correctness. Rejected for the first backend.

### D — low-address mapping

Mapping all relevant objects below 4 GiB could make some casts usable, but needs every referenced script, data object and writable global, supported executable/linker relocations, a safe null representation and platform-specific mapping guarantees. The observed native executable does not satisfy the address condition. No forced fixed mapping was attempted on the user's process; no evidence establishes availability across macOS/Linux/ASLR. This is fragile, difficult to debug, and unnecessary risk for a canonical backend. Rejected.

### E — ARM/GBA emulation — selected first implementation target

Executing the actual ARM build preserves four-byte script fields, original script/data addresses and target call behavior without translating interpreter widths. This minimizes mechanical code changes and permits deterministic checkpoint/instruction execution. A reviewed tournament controller/initialization patch is still needed for two independent AI trainers; emulation does not solve side asymmetries by itself.

[mGBA's official scripting API](https://mgba.io/docs/scripting.html) documents frame stepping, instruction stepping, memory access and save-state buffers; its [upstream repository](https://github.com/mgba-emu/mgba) is the implementation source. These capabilities support a potential harness, not an existing integration here. mGBA, arm-none-eabi-gcc and qemu-system-arm were not found on PATH. No complete pokeemerald ROM/ELF build was available (the small .gba data blobs are multiboot assets, not a game build). No emulator throughput was measured. Event extraction may use instrumented engine hooks plus memory traces; frame-level snapshots alone can miss transient events.

Performance will likely cost more than a native core, but correctness has priority. Pin emulator/build/checkpoint versions and hash traces. Debugging benefits from authentic addresses/symbols; maintenance concentrates on a small ARM-side adapter and emulator interface. Keep B as a later optimization validated differentially against E.

## Required modifications and gate

No upstream code has been modified. Required future patch scope: dedicated initialization entry/checkpoint, two ordinary party constructions without clearing the wrong buffer, independent trainer identity/AI history/inventories, NPC obedience on both sides, removal of player-only badge/friendship/experience privileges in tournament mode, deterministic controller acknowledgments, and non-RNG-consuming event hooks. The battle interpreter and operand widths should remain unchanged.

Accept only an actual engine run that constructs both parties, records full bytes, executes scripts and both-side AI, reaches a real outcome, and repeats the identical trace for the same seed. A different seed must have a traced, explainable stream difference; it need not change the winner. This integration target is still unmet. Local compiler/OT probes do not substitute for it.
